Checklists

Listas de verificação acionáveis para as etapas mais críticas do fluxo de design. Imprima, cole na parede ou abra antes de cada entrega.

Como usar

Percorra cada item antes de avançar de fase. Se um item não se aplica ao seu projeto, marque como N/A e siga em frente — o objetivo é pensar em cada ponto, não travar o projeto.

Checklist de Design System

Use ao criar ou avaliar um design system do zero. Serve tanto para sistemas pessoais quanto para times.

  • ☐ Paleta de cores definida: primária, secundária, neutros, semânticas (success, warning, danger, info)
  • ☐ Tokens de cor criados como Variables com suporte a modo claro e escuro
  • ☐ Tokens de tipografia: tamanhos de fonte, line-height, letter-spacing e peso para cada nível (Display, H1–H4, Body, Caption, Label)
  • ☐ Tokens de espaçamento: escala definida (ex.: 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 px)
  • ☐ Tokens de border-radius para cada "camada" de arredondamento
  • ☐ Tokens de sombra (shadow) para elevações (sm, md, lg)
  • ☐ Componentes atômicos construídos: botão, input, checkbox, radio, toggle, badge, avatar, ícone
  • ☐ Componentes moleculares: card, modal, tooltip, toast, dropdown, breadcrumb, pagination
  • ☐ Componentes usando Auto Layout (não posicionamento manual)
  • ☐ Variantes definidas para estados: default, hover, active, disabled, error, loading
  • ☐ Component Properties expostas (texto, booleanos, variantes, instance swap)
  • ☐ Biblioteca publicada no Figma (Assets → Publish)
  • ☐ Documentação de uso: cada componente com anotação de quando e como usar
  • ☐ Processo de atualização definido (quem aprova, como é comunicado ao time)
  • ☐ Equivalência com o código: componentes espelham os da biblioteca de frontend (React, Vue, etc.)

Checklist de Handoff para Desenvolvedores

Execute antes de compartilhar o link do arquivo com o time de engenharia.

  • ☐ Todos os frames de entrega estão em frames nomeados (não grupos soltos)
  • ☐ Camadas nomeadas de forma descritiva (não "Rectangle 47" ou "Group 12")
  • ☐ Dev Mode habilitado e o link de inspeção gerado
  • ☐ Todos os componentes são instâncias de componentes da biblioteca (não cópias soltas)
  • ☐ Imagens e ícones com marcação de exportação (Export) configurada com o formato correto (SVG para ícones, PNG/WebP para fotos)
  • ☐ Espaçamentos internos conferidos com a escala do token (múltiplos de 4 ou 8)
  • ☐ Comportamento responsivo documentado: qual frame é mobile, tablet, desktop
  • ☐ Estados de UI cobertos: vazio (empty state), carregando (loading/skeleton), erro, sucesso
  • ☐ Fluxo de protótipo disponível para estados de interação não óbvios
  • ☐ Anotações de interação adicionadas onde o comportamento não é visual (ex.: debounce, validação)
  • ☐ Fontes verificadas: todas são fontes do Google Fonts, sistema ou licenciadas
  • ☐ Cores usando styles/variables (não cores hardcoded em hex avulsas)
  • ☐ Contraste de cor conferido (mínimo AA pelo WCAG 2.2: 4,5:1 para texto normal)
  • ☐ Tamanhos de toque (touch targets) mínimos respeitados: 44×44 px (Apple HIG) ou 48×48 dp (Material)
  • ☐ Revisão do desenvolvedor agendada para tirar dúvidas antes da implementação

Checklist de Acessibilidade

Baseado nas diretrizes WCAG 2.2. Aplique a cada tela antes de aprovar para entrega.

Níveis WCAG

Nível A — obrigatório. Nível AA — padrão de mercado e exigência legal em vários países. Nível AAA — ideal para acessibilidade máxima. Mire sempre no AA.

  • ☐ Contraste de texto normal: mínimo 4,5:1 entre cor do texto e fundo (WCAG AA)
  • ☐ Contraste de texto grande (≥18 pt ou ≥14 pt negrito): mínimo 3:1
  • ☐ Contraste de elementos de UI interativos (bordas de input, ícones ativos): mínimo 3:1
  • ☐ Informação não depende só de cor: erros indicados também por ícone/texto, não só por cor vermelha
  • ☐ Tamanho de fonte mínimo: 16 px para corpo de texto principal
  • ☐ Espaçamento de texto: design suporta aumento de line-height (1,5×), letter-spacing (0,12 em) e word-spacing (0,16 em) sem quebrar layout
  • ☐ Targets tocáveis: áreas clicáveis de pelo menos 44×44 px
  • ☐ Foco visível: todos os elementos interativos têm um estado de foco claramente visível (anel de foco)
  • ☐ Navegação por teclado: ordem de foco lógica documentada (Tab order anotado nos frames)
  • ☐ Imagens decorativas anotadas como alt="" para leitores de tela
  • ☐ Imagens informativas com texto alternativo (alt) descrito na anotação
  • ☐ Ícones sem texto: possuem label acessível anotado (aria-label)
  • ☐ Formulários: cada campo tem label visível (não apenas placeholder)
  • ☐ Mensagens de erro: descrevem o problema e como corrigi-lo
  • ☐ Animações: há alternativa ou desativação para usuários com prefers-reduced-motion

Checklist "Antes de Entregar" — Revisão Final

O último pente fino antes de apresentar ao cliente, PO ou subir para produção.

  • ☐ Arquivo organizado: páginas nomeadas por fluxo ou sprint, não "Page 1", "Page 2"
  • ☐ Frames de entrega ordenados da esquerda para a direita no canvas na ordem do fluxo
  • ☐ Sem objetos esquecidos fora dos frames (na área geral do canvas)
  • ☐ Sem layers ocultas que não deveriam estar lá (limpe o que não será entregue)
  • ☐ Conteúdo real ou realista — sem "Lorem ipsum" em texto visível
  • ☐ Imagens de placeholder substituídas por imagens representativas
  • ☐ Todos os estados de componente presentes: default, hover, focus, active, disabled
  • ☐ Fluxo de prototipagem testado do início ao fim no Preview (Ctrl/⌘ + Alt/⌥ + ↵)
  • ☐ Versões mobile e desktop presentes (se o projeto for responsivo)
  • ☐ Arquivo salvo e sincronizado (verifique o indicador de status no canto superior)
  • ☐ Permissões de acesso configuradas (quem pode editar vs. apenas ver)
  • ☐ Link de compartilhamento testado em janela anônima (ou por outro usuário)
  • ☐ Changelog ou nota de versão adicionada ao arquivo ou à apresentação

Checklist de Auto Layout e Componentização

Para avaliar a qualidade técnica de componentes e frames construídos com Auto Layout.

  • ☐ Todos os contêineres que precisam crescer/diminuir usam Auto Layout (não posicionamento absoluto)
  • ☐ Espaçamentos usam o campo Gap do Auto Layout, não objetos espaçadores invisíveis
  • ☐ Padding configurado pelo painel de Auto Layout, não por margin manual dos filhos
  • ☐ Direção (horizontal/vertical) escolhida de forma intencional
  • ☐ Filhos com resizing correto: "Fixed" para tamanho rígido, "Fill container" para crescer, "Hug contents" para abraçar
  • ☐ Componentes com mais de 2 variações organizados em Component Sets (com Variants)
  • ☐ Nomes das propriedades de variante em inglês e descritivos (Type, Size, State, Hierarchy…)
  • ☐ Valores das propriedades consistentes entre variantes (ex.: todos usam "Small" não misturar "Small" e "sm")
  • ☐ Componentes testados com textos curtos E longos (evitar overflow)
  • ☐ Componentes testados com conteúdo de imagem faltando (graceful degradation)
  • ☐ Nested Auto Layouts (Auto Layout dentro de Auto Layout) usados corretamente para layouts complexos
  • ☐ Componentes de layout de página (header, footer, sidebar) construídos com Constraints além do Auto Layout
  • ☐ Sem grupos desnecessários dentro de Auto Layouts (Groups não interagem bem com resizing)
Dica de time

Transforme estas checklists em um arquivo Figma com checkboxes reais (retângulos + estados de componente) e cole na página de "QA" do seu arquivo. Isso torna a revisão visual e rastreável por toda a equipe.
