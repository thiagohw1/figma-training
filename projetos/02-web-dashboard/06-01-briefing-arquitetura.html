Briefing e arquitetura de informação

Todo projeto de design começa antes do Figma ser aberto. Nesta lição você vai conhecer o TaskFlow — o produto SaaS que construiremos juntos — e aprender a transformar um briefing em uma arquitetura de informação sólida.

⏱️ Leitura: ~20 min 🎯 Nível: Projeto prático 🛠️ Pratique no Figma

Ao final desta lição você será capaz de

  • Descrever o produto TaskFlow: público-alvo, problema resolvido e principais funcionalidades;
  • Construir um sitemap hierárquico no Figma para um SaaS de gestão de projetos;
  • Definir o escopo do MVP (Minimum Viable Product) e documentar as telas a serem criadas;
  • Mapear os fluxos de navegação mais críticos do produto;
  • Preparar o arquivo Figma com uma estrutura de páginas profissional antes de começar a desenhar.

Conhecendo o TaskFlow

O TaskFlow é um SaaS (Software as a Service) de gestão de projetos para times de médio porte — equipes de 5 a 50 pessoas que trabalham com projetos paralelos, prazos e entregáveis. Pense em uma alternativa mais focada ao Asana ou ao Monday.com: mais simples de adotar, com um dashboard de métricas que os gestores amam e um board Kanban que o time não abandona.

O problema que ele resolve

Times de produto, marketing e desenvolvimento perdem em média 2–3 horas por semana tentando entender "onde está cada tarefa" e "quem está travado em quê". O TaskFlow centraliza essa visibilidade em um único lugar, com atualizações em tempo real e uma hierarquia clara: Espaço de trabalho → Projeto → Lista → Tarefa.

Público-alvo

  • Gestores de projeto: precisam de visão geral (dashboard, timeline, carga do time).
  • Membros do time: precisam saber o que fazer hoje (Minhas tarefas, notificações).
  • Stakeholders: precisam de relatórios de progresso sem entrar no detalhe.
Por que um SaaS de gestão?

Aplicativos de gestão de projetos são o caso de uso perfeito para aprender design de produtos complexos: eles combinam tabelas de dados, formulários, componentes de status, navegação multi-nível, responsividade e uma hierarquia de informação densa — tudo o que você precisa dominar para trabalhar com dashboards reais.

Arquitetura de informação

A arquitetura de informação (IA) define quais telas existem, como se relacionam e como o usuário navega entre elas. Para um SaaS, isso costuma se traduzir em um sitemap e em fluxos de navegação.

O sitemap do TaskFlow

Sitemap simplificado do TaskFlow. Cada retângulo é uma tela ou estado de tela a ser projetado.

Fluxo de navegação principal

No TaskFlow, a navegação segue dois eixos:

  • Global (sidebar): Dashboard, Projetos, Minhas Tarefas, Membros, Configurações. Sempre visível no desktop.
  • Contextual (topbar e abas): dentro de um projeto, o usuário alterna entre as views (Lista, Board, Calendário).

Essa separação é intencional: a sidebar responde a "onde estou no produto?", enquanto as abas respondem a "como quero ver os dados deste projeto?".

Estrutura do arquivo Figma

Antes de criar o primeiro frame, profissionais organizam o arquivo em páginas dentro do Figma. Isso mantém tudo navegável e facilita o handoff com o time de desenvolvimento.

Passo a passo: organizando o arquivo

  1. Crie um novo arquivo. No Figma, vá em New design file. Renomeie-o imediatamente para "TaskFlow — Design System & UI" clicando duas vezes no nome no topo.
  2. Crie as páginas do projeto. Clique no + ao lado de "Page 1" no painel esquerdo para adicionar páginas. Crie as seguintes (nesta ordem):
    • 📋 Briefing & IA
    • 🎨 Fundação Visual
    • 🧩 Components
    • 🖥️ Desktop (1440)
    • 📱 Tablet (768)
    • 📲 Mobile (375)
    • 🌐 Landing Page
    • 🔗 Protótipo
  3. Na página "Briefing & IA", monte o sitemap. Use frames (F) como caixas e conecte-os com setas. Selecione dois frames e use Add connection no modo de protótipo, ou simplesmente crie linhas com a ferramenta de vetor (P). Mantenha tudo em tons de cinza — esta é a fase de estrutura, não de visual.
  4. Documente o escopo. Adicione um frame de texto ao lado do sitemap listando as telas do MVP. Use a ferramenta Texto (T) e crie uma hierarquia tipográfica simples (título, subtítulo, item).
  5. Crie frames-referência para as telas. Na página Desktop (1440), crie um frame com preset Desktop → 1440. Nomeie-o "01 — Dashboard". Isso reserva o espaço e cria a estrutura antes de qualquer design.
Convenção de nomenclatura

Profissionais usam prefixos numéricos (01 — Dashboard, 02 — Projetos) para manter os frames em ordem no painel de layers. Use — (em dash) como separador: fica mais legível do que traço simples.

Não pule a fase de IA

A tentação de abrir o Figma e já começar a desenhar é enorme. Mas designers que pulam a arquitetura de informação frequentemente precisam refatorar metade do projeto depois — porque descobrem que criaram telas que o usuário nunca acharia ou que duplicaram funcionalidades. Dedique 30 minutos ao mapa antes de tocar em pixels.

Exemplo de uso real

O processo descrito aqui é idêntico ao que times de produto usam em empresas como Nubank, iFood e Conta Azul antes de qualquer sprint de design. O designer de produto recebe o briefing (às vezes um PRD — Product Requirements Document), extrai as telas necessárias, mapeia os fluxos críticos e só então começa a explorar visuais. O Figma é o artefato que documenta essa IA para toda a equipe.

Resumo

  • O TaskFlow é um SaaS de gestão de projetos para times de 5–50 pessoas, com dashboard, Kanban, tarefas e membros.
  • A arquitetura de informação (sitemap + fluxos) deve ser feita antes de qualquer design visual.
  • O arquivo Figma deve ter uma estrutura de páginas clara desde o início: Briefing, Fundação Visual, Components, frames de breakpoint, Landing Page e Protótipo.
  • O escopo do MVP é definido com MoSCoW para evitar feature creep nas primeiras iterações.
  • Nomenclatura consistente (01 — NomeDaTela) mantém o projeto navegável conforme cresce.
✍️ Exercício

Monte o arquivo base do TaskFlow

Crie o arquivo no Figma e configure sua estrutura:

  1. Crie um novo arquivo e nomeie-o "TaskFlow — [seu nome]".
  2. Crie as 8 páginas conforme a lista do passo a passo (use os emojis e nomes exatos).
  3. Na página Briefing & IA, reproduza o sitemap usando frames e linhas — sem cores, apenas estrutura.
  4. Na página Desktop (1440), crie 5 frames com o preset Desktop 1440 e nomeie-os de 01 a 05 com os nomes das telas do MVP.
Critério de sucesso: o arquivo tem 8 páginas nomeadas corretamente, a página de briefing contém um sitemap legível e a página desktop tem 5 frames nomeados — tudo antes de qualquer pixel de visual.
🏆 Desafio

Mapeie um fluxo de criação de tarefa

No modo de Protótipo do Figma, conecte os 5 frames que você criou para simular o fluxo de um usuário que entra no dashboard, clica em um projeto, abre o board Kanban e cria uma nova tarefa. Inclua pelo menos um modal (frame flutuante) representando o formulário de criação de tarefa. Use a função Smart Animate na transição para o modal e documente o fluxo com anotações de texto.

QuizTeste seu conhecimento

1. Qual é a hierarquia correta de navegação no TaskFlow?

  • Tarefa → Lista → Projeto → Espaço de trabalho
  • Projeto → Espaço de trabalho → Lista → Tarefa
  • Espaço de trabalho → Projeto → Lista → Tarefa
  • Lista → Projeto → Tarefa → Espaço de trabalho
A hierarquia correta é do mais abrangente ao mais específico: Espaço de trabalho → Projeto → Lista → Tarefa. Esse padrão é comum em ferramentas como Asana e ClickUp.

2. No framework MoSCoW, o que significa "Must have"?

  • Funcionalidade desejável mas que pode ficar para a v2
  • Funcionalidade obrigatória para o produto ser viável no lançamento
  • Funcionalidade que provavelmente nunca será implementada
  • Funcionalidade que o time adoraria ter mas não há tempo
Must have são requisitos essenciais — sem eles, o produto não pode ser lançado. São o núcleo do MVP.

3. Por que separar a sidebar (navegação global) das abas (views contextuais)?

  • A sidebar responde "onde estou no produto?" e as abas respondem "como vejo os dados deste contexto?"
  • É apenas uma convenção estética — poderiam ser unificadas sem impacto na UX
  • A sidebar é para mobile e as abas são para desktop
  • As abas são mais rápidas de implementar no código
A separação é funcional: a sidebar é a navegação global (entre seções do produto) e as abas são a navegação local (entre visualizações de um mesmo contexto). Misturá-las cria confusão cognitiva no usuário.
