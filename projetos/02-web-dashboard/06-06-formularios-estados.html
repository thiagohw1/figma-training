Formulários e estados

Formulários são onde os usuários constroem o produto — criam projetos, adicionam tarefas, convidam membros. Projetar formulários bem é projetar a experiência de entrada de dados: clara, tolerante a erros e que dá feedback imediato.

⏱️ Leitura: ~26 min 🎯 Nível: Projeto prático 🛠️ Pratique no Figma

Ao final desta lição você será capaz de

  • Criar um Component de Input com todos os estados (default, focus, filled, error, disabled);
  • Construir Select, Checkbox, Radio Button, Toggle e Date Picker como Components;
  • Projetar mensagens de validação e feedback visual coerentes com os tokens semânticos;
  • Criar os estados de tela mais importantes: Empty State, Loading Skeleton, Error e Success;
  • Montar um Modal e um Drawer (panel lateral) como overlays do sistema.

O Component de Input

O Input é o componente de formulário mais ubíquo — e o mais importante de acertar. Ele precisa comunicar claramente em qual estado está (vazio? preenchido? com erro?) sem poluir a tela com informações desnecessárias.

Anatomia do Input

  • Label: texto acima do campo (Body/13 Medium, color/text/default). Obrigatório para acessibilidade.
  • Field: o input em si — borda, fundo, placeholder/valor, ícones laterais.
  • Helper text: texto abaixo — instrução (cor muted) ou mensagem de erro (cor danger).

  1. Crie o frame base do Input. Frame com Auto Layout vertical, gap 6. Dentro: Label (Text property), Field (frame horizontal 360×44 px, padding 12, gap 8), Helper text (Text property + booleana para visibilidade).
  2. Configure o Field. Auto Layout horizontal, gap Auto, padding 0 12. Conteúdo: ícone esquerdo (opcional, Instance Swap), texto do campo, ícone direito (opcional). O texto usa Instance Swap para alternar entre placeholder e valor digitado. Borda: Stroke Outside 1 px, border-radius 8.
  3. Crie as 5 Variants de State. Adicione a propriedade State com os valores: default, focus, filled, error, disabled. Em cada variant, mude as cores de borda e fundo conforme a tabela acima.
  4. Adicione a propriedade de erro. Na variant error, o helper text muda de cor (color/semantic/danger) e adicione um ícone de alerta (⚠️ 14×14 px) no lado direito do field. Use uma Boolean property Has error para controlar a visibilidade do helper text de erro.
  5. Salve como Component. Nomeie Form/Input. Propriedades expostas: Label text, Placeholder text, Value text, State (variant), Has leading icon (boolean), Has trailing icon (boolean), Helper text, Has error.
Label flutuante (floating label)

Em produtos SaaS modernos, a label às vezes "flutua" — começa dentro do campo como placeholder e sobe para o topo quando o usuário clica. Isso é elegante mas complexo de implementar no Figma com protótipo. Para começar, use o padrão mais simples: label acima + placeholder dentro. Mais claro para o usuário e mais fácil de codar.

Outros componentes de formulário

Select (Dropdown)

Component com o mesmo visual do Input mas com ícone de chevron-down fixo na direita e um dropdown de opções. Variants: closed/open. No estado open, o frame de opções aparece abaixo com sombra Shadow/md.

Checkbox

Quadrado de 18×18 px, border-radius 4, borda 1.5 px. Variants de State: unchecked (borda border-strong), checked (fundo primary, ícone checkmark branco), indeterminate (traço horizontal branco — para "selecionar todos" parcial), disabled. Crie o CheckboxField combinando Checkbox + Label + Helper text em Auto Layout horizontal.

Radio Button

Círculo de 18×18 px, borda 1.5 px. Variants: unchecked, checked (círculo interno de 8 px na cor primary). Sempre use dentro de um RadioGroup — Radio Buttons nunca aparecem isolados.

Toggle (Switch)

Track oval de 40×24 px com thumb circular de 18×18 px. Variants: off (track cinza, thumb à esquerda), on (track primary, thumb à direita). Adicione uma animação Smart Animate no protótipo para suavizar a transição.

Date Picker

Input com ícone de calendário. No estado open: popover de 280×300 px com cabeçalho de mês/ano, navegação para anterior/próximo, e grid de dias (7 colunas × 5 linhas). Variants do Day Cell: default, hover, today (círculo de fundo muted), selected (círculo primary), range (fundo primary-soft para intervalos de datas).

Estados de tela do sistema

Todo fluxo de usuário passa por múltiplos estados antes de mostrar o conteúdo final. Projetar esses estados é fundamental para que a interface pareça completa e polida — não apenas na tela "feliz".

Empty State

Aparece quando não há dados para exibir (ex.: nenhum projeto criado ainda). Um bom Empty State tem: ícone ou ilustração, título claro, texto explicativo e um CTA primário para resolver o vazio.

  1. Crie o frame do Empty State. Frame com Auto Layout vertical, align center, gap 12, padding 48. Dentro: ícone (48×48 px, border-radius 12, fundo surface-2), título (h2), descrição (Body/14, muted, max-width 360 px, text-align center), botão primário CTA.
  2. Crie Variants por contexto. Propriedade Context: projects (ícone de pasta), tasks (ícone de checklist), members (ícone de grupo), search-results (ícone de lupa). Cada variant muda o ícone e o texto.

Loading Skeleton

O skeleton substitui o conteúdo enquanto os dados carregam — muito melhor que um spinner no centro da tela porque comunica a estrutura da página que está chegando.

Para criar um skeleton no Figma: substitua os textos por retângulos arredondados (border-radius 4 px) com fill usando um gradiente shimmer animado (surface-2 → surface-3 → surface-2). No protótipo, use uma animação de After delay que transita do skeleton para o estado carregado.

Error State

Quando uma operação falha (erro de servidor, timeout), mostre uma tela de erro com: ícone de alerta, mensagem clara do que deu errado (sem jargão técnico), e botão "Tentar novamente".

Nunca mostre mensagens técnicas ao usuário

Erros como "Error 500: Internal Server Error" ou "TypeError: Cannot read property of undefined" são para desenvolvedores, não para usuários. No design, escreva mensagens empáticas: "Não conseguimos carregar seus projetos agora. Tente novamente em instantes." O código de erro pode aparecer em menor destaque para suporte técnico.

Success State

Confirme ações importantes com feedback visual: toast/snackbar aparece no canto da tela (bottom-right) com ícone de check + mensagem de sucesso (ex.: "Projeto criado com sucesso!"). Desaparece automaticamente após 4 segundos. Para ações críticas (excluir projeto), use um modal de confirmação antes da ação.

Modal e Drawer

Modal

O Modal é uma camada de overlay que para o fluxo principal para executar uma ação focada. Estrutura: backdrop escuro (fundo rgba(0,0,0,.5) no frame acima do conteúdo) + painel centralizado (max-width 560 px, padding 28, border-radius 16, Shadow/lg).

O painel tem: header (título + botão X de fechar), corpo com formulário ou conteúdo, footer com botões de ação (cancelar + confirmar, alinhados à direita).

Drawer (Panel lateral)

O Drawer aparece pela direita (ou esquerda) como um painel que desliza sobre o conteúdo sem substituí-lo completamente. Ideal para detalhes que precisam de mais espaço (detalhe de tarefa, configurações de projeto). Largura: 400–480 px, ocupa 100% da altura da viewport menos a topbar.

Dica: modal vs. drawer vs. página

Use modal para ações curtas e destrutivas (confirmar exclusão, criar item com poucos campos). Use drawer para detalhes ricos que o usuário precisa referenciar enquanto olha o contexto. Use página nova quando o conteúdo é extenso ou precisa de navegação própria (edição completa de um projeto). Misturar os três sem critério cria interfaces confusas.

Exemplo de uso real

A Linear (ferramenta de issue tracking usada por times de engenharia) é famosa pela qualidade dos seus formulários e estados: os skeletons carregam instantaneamente antes dos dados, os empty states são específicos por contexto, e os modais têm atalhos de teclado (Esc para fechar, Enter para confirmar). Essas micro-decisões de UX são definidas primeiro no design.

Resumo

  • O Component Input precisa de 5 variants de estado (default, focus, filled, error, disabled) com propriedades expostas para label, placeholder, value e helper text.
  • Checkbox, Radio, Toggle e Select são components independentes — nunca copie e cole ajustando manualmente.
  • Empty State, Loading Skeleton, Error e Success são estados de tela tão importantes quanto o estado "carregado".
  • Skeletons comunicam estrutura enquanto carregam — muito superiores a spinners centralizados.
  • Modais para ações curtas; Drawers para detalhes ricos; páginas para conteúdo extenso.
  • Nunca mostre mensagens de erro técnicas ao usuário — escreva linguagem empática e clara.
✍️ Exercício

Construa o formulário "Criar Tarefa"

  1. Crie o Component Form/Input com as 5 variants de estado e todas as propriedades expostas.
  2. Monte um Modal de "Criar Tarefa" usando o Input, um Select de responsável, um Date Picker e um Toggle de prioridade.
  3. Projete o estado de loading skeleton do painel de tarefas: substitua os cards de tarefa por retângulos arredondados de fundo surface-2.
  4. Crie um Empty State para a tela de projetos (quando o usuário ainda não criou nenhum).
Critério de sucesso: o Modal de "Criar Tarefa" tem todos os campos com labels visíveis, o estado de error mostra a borda vermelha e o helper text de erro no Input de nome, e o Empty State tem CTA claro que leva ao modal de criação.
🏆 Desafio

Fluxo completo de criação com validação

Monte o fluxo completo de criação de projeto no protótipo: (1) tela de lista de projetos no Empty State → clique no CTA abre o Modal → (2) Modal com formulário no estado default → digitar no campo de nome o muda para focus → (3) clicar em "Criar" sem preencher o nome obrigatório mostra o Input no estado error com helper text → (4) preencher corretamente e clicar confirma, fecha o modal e exibe o Toast de sucesso na tela principal. Use interações de Set variable para gerenciar os estados do Input.

QuizTeste seu conhecimento

1. Qual é a principal vantagem do Loading Skeleton sobre um spinner centralizado?

  • O skeleton carrega mais rápido no servidor
  • O skeleton comunica a estrutura da página que está chegando, reduzindo a percepção de espera e evitando o salto visual (layout shift) quando os dados chegam
  • O spinner é mais acessível para usuários com deficiências visuais
  • Skeletons são mais fáceis de implementar em código
O skeleton elimina o layout shift — a página "pula" quando o conteúdo substitui o spinner. Além disso, comunicar a estrutura reduz a percepção de espera (o cérebro processa "está carregando" em vez de "está travado").

2. Quando usar um Drawer em vez de um Modal?

  • Drawer sempre que o usuário precisar confirmar uma ação destrutiva
  • Modal para formulários com muitos campos; Drawer para ações rápidas
  • Drawer quando o usuário precisa ver o contexto principal enquanto acessa detalhes ricos; Modal para ações focadas e curtas
  • Drawer é exclusivo para mobile; Modal é para desktop
Drawer desliza sobre o conteúdo sem esconder completamente o contexto — ideal para o detalhe de uma tarefa onde o usuário ainda quer ver o board ao fundo. Modal para, bloqueando o fundo, indicando que o usuário deve concluir aquela ação antes de prosseguir.

3. Um campo de Input está inválido. Qual combinação de mudanças visuais deve ocorrer para comunicar o erro corretamente?

  • Borda vermelha (danger) + fundo danger-soft + ícone de alerta à direita + helper text em vermelho abaixo
  • Apenas o texto do placeholder muda para vermelho
  • Um pop-up de alerta abre sobre o campo
  • O campo pisca 3 vezes
O estado de erro usa múltiplas camadas de feedback: cor (borda + fundo), ícone (alerta), e texto (helper text explicativo). Usar apenas uma camada (ex.: só mudar a cor) falha em acessibilidade — usuários com daltonismo podem não perceber.
