Estados, dark mode e responsividade

Uma tela só existe em um estado. Um produto real existe em dezenas: loading, erro, vazio, cheio, dark, light, em telas diferentes. Nesta lição você vai dominar os estados do FinView, aplicar dark mode via Variable Modes e preparar o design para múltiplos tamanhos de tela mobile.

⏱️ Leitura: ~25 min 🎯 Nível: Projeto prático 🛠️ Pratique junto no Figma

Ao final desta lição você será capaz de

  • Criar os estados Loading (skeleton), Empty e Error para as telas do FinView;
  • Aplicar Variable Modes para trocar entre Light e Dark em um único clique;
  • Adaptar as telas para tamanhos de tela mobile diferentes (iPhone SE, iPhone 16 Pro Max, Android);
  • Usar Constraints e Fill para que elementos se adaptem à largura da tela;
  • Respeitar as safe areas em diferentes modelos de iPhone.

Estados de interface: além do estado padrão

Todo designer iniciante projeta o "happy path" — a tela perfeita com dados bonitos. Mas os usuários reais encontram situações muito diferentes: o primeiro acesso ao app (vazio), a internet caiu (erro), os dados estão carregando (loading). Projetar apenas o estado padrão é como construir uma casa sem pensar em chuva.

Para o FinView, os estados críticos são:

Loading (Skeleton)App abrindo, sincronizandoPlaceholders animados em cinza
EmptyPrimeiro acesso, sem transaçõesIlustração motivadora + CTA de "Adicionar primeira transação"

Partial emptyTem saldo mas não tem metaCard de meta com CTA "Criar sua primeira meta"
O que é um Skeleton Screen?

Um skeleton screen (tela esqueleto) é uma representação do layout da tela com blocos cinzas no lugar do conteúdo real, exibida durante o carregamento. Popularizada por apps como LinkedIn e Facebook, ela é preferível ao tradicional spinner porque comunica a estrutura da tela que vai chegar — reduzindo a sensação de espera. No Figma, você cria um skeleton duplicando a tela default e substituindo todos os textos e ícones por retângulos cinzas com bordas arredondadas.

Construindo o estado Skeleton da Home

  1. Duplique o frame da Home padrão. Na page iOS, selecione o frame 01 — Home e duplique (Ctrl/⌘ + D). Renomeie para 01 — Home (Loading). Posicione ao lado do frame original.
  2. Substitua o card de saldo por skeleton. Selecione a área de texto do valor principal. Troque por um retângulo de 160×28 px, fill #2B313C (em dark mode), corner radius 6. Faça o mesmo com os textos de receita e gasto — retângulos mais estreitos.
  3. Substitua os cartões de conta. Cada card de conta vira um retângulo de 140×80 px com fill #222731, radius 12. Sem texto interno.
  4. Substitua os itens da lista. Para cada item de transação: o ícone vira um quadrado 44×44 radius 12 em #2B313C; o texto do nome vira um retângulo 120×12 radius 4; a categoria vira um retângulo 80×10 radius 4; o valor vira um retângulo 60×14 radius 4. Use opacidade diferente (o bloco mais escuro = mais destaque) para criar hierarquia visual mesmo no skeleton.
  5. Adicione o efeito de shimmer (opcional mas recomendado). No Figma, a animação de shimmer (brilho deslizante) é simulada com um gradiente linear de branco a transparente em 90°, aplicado sobre os retângulos de skeleton. Para animar no protótipo, use Smart Animate — veremos na Lição 7.

Passo a passo: aplicando Dark Mode com Variable Modes

Nas lições anteriores criamos a coleção Semantic/Colors com os modos Light e Dark. Agora vamos criar as versões light de todas as telas principais:

  1. Duplique as telas para criar versões Light. Selecione todos os frames na page iOS (Ctrl/⌘ + A). Duplique (Ctrl/⌘ + D). Mova as cópias para uma nova linha abaixo das originais com 40 px de espaçamento. Renomeie adicionando " — Light" no final: 01 — Home — Light.
  2. Troque o Variable Mode dos frames copiados. Selecione o frame 01 — Home — Light. No painel direito, em Layer, procure a seção de Variable Modes (aparece como um seletor de pill abaixo do nome do frame). Mude de Dark para Light. Observe a tela inteira mudando de cor instantaneamente.
  3. Verifique os elementos que não mudaram. Alguns elementos podem não ter mudado — provavelmente porque usam cores hardcoded (hex digitado diretamente) em vez de variables. Selecione cada um e troque para a variable semântica correta. Esses são os "buracos" no sistema de tokens.
  4. Ajuste os gradientes para light mode. O card de saldo usa um gradiente. Gradientes lineares com múltiplas paradas não suportam variables diretamente. A solução: crie uma variante do card (BalanceCard/Light) com um gradiente diferente (mais claro, ex.: violeta médio para roxo). Alterne a instância via component property.
  5. Documente a paleta light na page de Design Tokens. Adicione um frame na page de tokens mostrando as telas Home Dark e Home Light lado a lado, com anotações de quais tokens mudaram. Isso é o "entregável de dark mode" para a documentação do design system.
Verifique contraste em AMBOS os modos

Uma cor que tem contraste adequado no dark mode pode falhar no light mode. Use o plugin Contrast ou A11y - Color Contrast Checker no Figma para verificar o ratio de contraste (mínimo WCAG AA: 4.5:1 para texto normal, 3:1 para texto grande e elementos gráficos). No FinView, o verde de receita (#18C98A) sobre fundo branco precisa ser checado — pode precisar de um tom mais escuro no light mode.

Responsividade mobile: safe areas e tamanhos de tela

Dispositivos iOS têm áreas de sistema que não devem ser usadas pelo app: o Dynamic Island / notch na parte superior e o indicador de Home na parte inferior. Essas são as safe areas.

DispositivoResolução lógicaSafe area topSafe area bottom
iPhone SE (3rd gen)375×667 pt20 pt (status bar)0 pt (botão Home físico)
iPhone 16390×844 pt59 pt (Dynamic Island)34 pt (home indicator)
iPhone 16 Pro Max440×956 pt62 pt (Dynamic Island)34 pt (home indicator)
Android (Pixel 8)393×851 dp24 dp (status bar)Variável (barra de gestos)

No Figma, use um frame de safe area como guia: crie um retângulo com fill azul 10% de opacidade representando as zonas proibidas (top safe area + bottom safe area) e coloque-o como overlay no frame de tela. Seus elementos de UI não devem se sobrepor a essas áreas.

Adaptando a Home para iPhone SE

O iPhone SE tem uma tela significativamente menor (375×667 vs. 390×844). Elementos que cabem bem no iPhone 16 podem ficar apertados. Estratégias de adaptação:

  • Reduzir o card de saldo: de 180 px para 150 px de altura, reduzindo o font-size do valor.
  • Remover o carrossel de cartões ou reduzir a altura dos cards de conta de 80 para 64 px.
  • Usar Constraints: todos os elementos com largura Fill se adaptam automaticamente à largura do frame (375 vs. 390 px).
Teste sempre no menor dispositivo suportado

Designers tendem a trabalhar em telas grandes e testar em iPhones novos. Mas uma parte significativa dos usuários usa dispositivos mais antigos e menores. Se o design funciona bem no iPhone SE (375×667), ele funcionará em todos os outros. Adicione sempre um frame de iPhone SE ao lado do iPhone 16 para "stress test" visual da tela.

Usando Constraints para responsividade

Constraints no Figma definem como um elemento se comporta quando o frame pai muda de tamanho. Para que o FinView funcione em múltiplos tamanhos de tela, configure:

ElementoConstraint horizontalConstraint vertical
Card de saldoLeft + Right (stretch)Top (fixo ao topo)
Ícone do usuário no headerRight (fixo à direita)Top
Tab BarLeft + Right (stretch)Bottom (fixo ao rodapé)
Botão de ação flutuanteRightBottom
Lista de transaçõesLeft + Right (stretch)Top + Bottom (stretch)

Para aplicar: selecione o elemento dentro de um frame que não tem Auto Layout. No painel direito, em Constraints, defina as direções. Nota: dentro de frames com Auto Layout, os constraints de posição não se aplicam — mas os de tamanho (Fill/Hug/Fixed) funcionam.

Auto Layout > Constraints para responsividade

Para responsividade real, Auto Layout com largura Fill é mais poderoso que Constraints. Um elemento filho com width=Fill dentro de um Auto Layout parent sempre ocupa todo o espaço disponível, independente do tamanho do frame pai. Reserve Constraints para elementos que não estão dentro de um Auto Layout, como overlays e elementos posicionados absolutamente.

Estado de Erro

A tela de erro deve ser amigável, não técnica. Para o FinView, o estado de erro na Home mostra:

  • Um ícone de Wi-Fi desconectado ou nuvem com X (ilustração simples)
  • Título: "Não conseguimos carregar seus dados"
  • Subtítulo: "Verifique sua conexão e tente novamente"
  • Botão primário: "Tentar novamente"
  • Link secundário: "Ver dados offline" (se o app suportar cache)

O card de saldo e a lista ficam visíveis mas em estado skeleton — comunicando que os dados existem, só não foram atualizados. Isso é o padrão "stale content + error overlay" comum em apps modernos.

Resumo

  • Estados críticos para o FinView: Default, Loading (skeleton), Empty, Error e Partial empty.
  • Skeleton screens comunicam a estrutura da tela durante o carregamento, reduzindo a percepção de espera.
  • Variable Modes permitem trocar entre Dark e Light no frame inteiro com um único clique — desde que todos os elementos usem tokens semânticos.
  • Safe areas variam por modelo: iPhone 16 tem 59 pt no topo (Dynamic Island) e 34 pt na base; iPhone SE tem apenas 20 pt no topo.
  • Constraints e Auto Layout com Fill garantem que o design se adapte a diferentes larguras de tela.
✍️ Exercício

Criar todos os estados da Home

No seu arquivo FinView, crie 4 versões do frame Home na page iOS:

  1. 01 — Home — estado padrão (dark)
  2. 01 — Home (Light) — estado padrão em light mode
  3. 01 — Home (Loading) — skeleton com placeholders cinzas em todos os elementos dinâmicos
  4. 01 — Home (Empty) — estado vazio com ilustração e CTA
Critério de sucesso: a versão Light usa exatamente as mesmas variables semânticas que a Dark — apenas o Variable Mode é diferente, não os tokens aplicados. O skeleton reproduz fielmente a estrutura da Home padrão.
🏆 Desafio

Adaptar o FinView para iPhone SE

Crie uma versão da Home otimizada para o iPhone SE (375×667 pt). O desafio: todo o conteúdo crítico (saldo, pelo menos 3 transações e a tab bar) deve ser visível sem scroll nessa tela menor. Isso vai exigir reduzir alturas, adaptar tamanhos de fonte e talvez remover elementos menos críticos. Documente no frame quais ajustes foram necessários e por quê — como uma nota de decisão de design. Dica: crie um frame de overlay com a safe area do SE para guiar seu design.

QuizTeste seu conhecimento

1. O que é uma "safe area" em design mobile iOS?

  • A área do frame que pode ser clicada sem risco de toque acidental
  • A região da tela que não é coberta por elementos de sistema (Dynamic Island, home indicator), onde o conteúdo do app deve ficar
  • Um constraint que impede elementos de sair do frame
  • A resolução mínima que uma imagem deve ter para não pixelar
Safe areas são as regiões da tela que ficam fora dos elementos de sistema do iOS (Dynamic Island, status bar, home indicator). O conteúdo do app deve respeitar essas margens para não ficar coberto pelo sistema. Diferentes modelos de iPhone têm safe areas com dimensões diferentes.

2. Por que um skeleton screen é preferível a um spinner de loading genérico?

  • Porque spinners consomem mais memória do dispositivo
  • Porque spinners não funcionam em dark mode
  • Porque o Figma não suporta animação de spinners
  • Porque o skeleton comunica a estrutura da tela que vai chegar, reduzindo percepção de espera e orientando o usuário
O skeleton screen reduz a percepção de espera ao mostrar a estrutura do conteúdo que está carregando — o usuário sabe exatamente o que vai aparecer. Um spinner genérico deixa o usuário sem referência. Pesquisas de UX mostram que skeleton screens são percebidos como carregamento mais rápido mesmo quando o tempo real é o mesmo.

3. Qual abordagem é mais eficiente para responsividade mobile no Figma?

  • Auto Layout com children em width=Fill — os elementos preenchem automaticamente o espaço disponível
  • Criar um frame separado para cada tamanho de tela, duplicando todos os elementos
  • Usar apenas Constraints com Left+Right em todos os elementos
  • Definir posições X fixas para cada elemento em cada tamanho de tela
Auto Layout com Fill é a abordagem mais eficiente: ao definir a largura de um elemento filho como Fill, ele automaticamente ocupa o espaço disponível no parent. Quando o frame pai muda de 390 para 375 px (iPhone 16 → SE), os elementos Fill se ajustam sem intervenção manual — exatamente como Flexbox no CSS.
