Documentação do Design System

Um Design System sem documentação é uma caixa preta. A documentação é o que transforma seu DS de "aquele arquivo que o time não sabe como usar" em uma ferramenta que autonomiza designers e desenvolvedores.

⏱️ Leitura: ~24 min 🎯 Nível: Avançado 🛠️ Pratique no Figma

Ao final desta lição você será capaz de

  • Adicionar descriptions em components e variables para documentação inline no Figma;
  • Criar páginas de documentação visual dentro do arquivo de DS (Do's & Don'ts, exemplos de uso);
  • Usar Annotations para comunicar intenção de design diretamente nas telas;
  • Avaliar ferramentas externas de documentação (Zeroheight, Supernova, Storybook);
  • Estabelecer um processo para manter a documentação atualizada ao longo do tempo.

Por que documentar?

Imagine um botão primário no seu DS. Você sabe que deve ser usado para a ação principal de uma tela, que deve aparecer apenas uma vez por página, e que nunca deve ser usado em contextos destrutivos. Mas se isso não estiver documentado, cada designer vai tomar essa decisão por conta própria — e o resultado será inconsistente.

Documentação não é overhead: é o multiplicador do seu DS. Cada hora que você investe em documentar bem economiza dezenas de horas em perguntas, erros e retrabalho do time.

Os três públicos da documentação

Designers precisam entender quando e como usar cada componente. Desenvolvedores precisam entender as propriedades, tokens e comportamentos. Product managers e stakeholders precisam entender os princípios e o porquê das decisões. Uma boa documentação fala com os três.

Documentação inline no Figma

O Figma oferece campos de documentação diretamente na interface que aparecem nos painéis do inspector e do Dev Mode — sem precisar de nenhuma ferramenta externa.

Descriptions em Components

Cada componente tem um campo de Description acessível ao clicar no componente no painel de Assets ou ao selecionar o Main Component. Para adicionar:

  1. Selecione o Main Component. No canvas, clique duas vezes até selecionar o componente principal (não uma instância). O painel direito mostra as propriedades do componente.
  2. Localize o campo Description. Na seção superior do painel direito, há um campo "Description" com placeholder "Add description". Clique nele para editar.
  3. Escreva a documentação. Inclua: para que serve o componente, quando usá-lo, quando NÃO usá-lo, variantes disponíveis e quaisquer regras de uso. Markdown básico é suportado (bold, listas).
  4. Adicione links relevantes. Abaixo do Description, há um campo para um Link (Documentation link). Cole a URL da documentação externa correspondente (Zeroheight, Storybook, Confluence…).
Description no Dev Mode

A Description que você escreve no componente aparece diretamente no Dev Mode quando um desenvolvedor inspeciona uma instância. Isso significa que a documentação viaja junto com o componente — sem precisar abrir outro documento.

Descriptions em Variables

Variables também têm campo de Description, acessível via Edit Variable (clique direito na variable). Use para documentar:

  • O propósito do token ("Cor de fundo para superfícies elevadas (cards, modais)");
  • Quando usar vs. quando usar outro token similar;
  • Qual contraste mínimo esperar com tokens de texto sobre esse fundo;
  • Referências ao token equivalente no código ("CSS: --color-bg-surface").

Páginas de documentação no Figma

Além da documentação inline, crie páginas dedicadas no arquivo de DS para cada categoria de componente. A estrutura clássica de uma página de documentação de componente:

Anatomia da página de documentação

  1. Header: nome do componente, status (stable/beta/deprecated), versão e quem mantém;
  2. Overview: o que o componente faz, em 1–2 frases;
  3. Anatomia: o componente com setas e labels identificando cada parte;
  4. Variantes: grade com todas as variantes lado a lado com nome e quando usar cada;
  5. Do's & Don'ts: exemplos corretos e incorretos de uso (veja abaixo);
  6. Comportamento: estados (hover, focus, active, disabled, loading, error), responsividade;
  7. Acessibilidade: notas de ARIA, navegação por teclado, contraste mínimo;
  8. Conteúdo: guia de microcopy — como escrever os textos dos componentes;
  9. Uso em contexto: o componente em telas reais, não em isolamento.

Do's e Don'ts

A seção mais impactante de qualquer documentação. O padrão visual é: dois frames lado a lado, um com uma borda verde e rótulo "Do" (correto), outro com borda vermelha e rótulo "Don't" (incorreto), cada um com uma breve explicação.

✓ Do
Salvar alterações

Use rótulos de ação claros e específicos que descrevem o que acontece ao clicar.

✗ Don't
OK

Evite rótulos genéricos que não comunicam a consequência da ação.

Padrão visual de Do's & Don'ts: borda verde para correto, vermelha para incorreto, explicação curta abaixo de cada exemplo.

Annotations — comunicação inline nas telas

Annotations (Figma 2024+) são marcadores que você pode adicionar diretamente sobre frames e componentes para comunicar intenção de design sem precisar usar sticky notes ou setas manuais. Elas ficam visíveis no Dev Mode com informações estruturadas:

  • Para acessar: com um elemento selecionado, vá em Inspect → Add annotation, ou use o ícone de Annotation na toolbar;
  • Você pode anotar propriedades específicas (padding, radius, interaction) com campos estruturados;
  • Annotations aparecem como balões numerados no canvas — o desenvolvedor clica para ver o detalhe;
  • Use para documentar comportamentos que não ficam óbvios pelo visual: "ao rolar 80 px, este header colapsa"; "este input valida em blur, não em keypress".
Annotations vs. Dev Mode specs

O Dev Mode já extrai automaticamente valores de spacing, tamanho e cores das variables. Use Annotations para complementar com informações que o Dev Mode não captura automaticamente: comportamentos interativos, regras de negócio, limites de conteúdo, dependências com outros sistemas.

Exemplos de uso contextual

Um dos maiores problemas de documentação de DS é mostrar componentes sempre em isolamento — o designer entende o botão, mas não sabe como combiná-lo com um Input para fazer um form válido. Crie páginas de Uso em Contexto:

  • Telas de exemplo: telas completas (não wireframes) mostrando os componentes em uso real — tela de login, tela de configurações, tela de checkout;
  • Patterns documentados: como combinar componentes para criar flows — "Form de múltiplos passos", "Lista com filtros e paginação";
  • Anti-patterns: exemplos do que não fazer em nível de pattern (não só componente individual).

Comece dentro do Figma

Para a maioria dos times pequenos e médios, documentar dentro do próprio arquivo Figma (descriptions + páginas de docs) é suficiente e tem a vantagem de ficar junto dos componentes, sempre atualizado. Ferramentas externas adicionam overhead de manutenção — só adote quando a necessidade for clara.

Mantendo a documentação atualizada

A maior dívida técnica de um DS é a documentação desatualizada. Um componente muda, mas a docs continua mostrando o comportamento antigo — criando confusão e desconfiança.

Processo para manter a consistência

  • Docs como parte da Definition of Done: nenhum componente é considerado "done" até que a description, a página de docs e os Do's & Don'ts estejam completos e revisados;
  • Update docs junto com o componente: quando um componente é modificado, atualizar a documentação faz parte da mesma tarefa — não é uma tarefa separada opcional;
  • Revisão periódica de docs: a cada trimestre, percorra as páginas de documentação e verifique se ainda refletem a realidade dos componentes;
  • Responsável pela documentação: designar uma pessoa como "dono" de cada seção do DS garante que há accountability;
  • Feedback loop: crie um canal (Slack, GitHub Issues, Notion) onde consumidores do DS possam reportar documentação incorreta ou ausente.
Documentação desatualizada é pior que nenhuma

Se um designer lê que o botão primário deve ser usado "sempre que houver uma ação principal", mas o botão que ele está usando já tem 3 variantes novas com regras diferentes, a documentação não apenas não ajuda — ela ativamente causa erros. Prefira documentação simples e correta a documentação completa e errada.

Exemplo de uso real

O DS "Aurora" de uma startup de SaaS tem a seguinte estratégia de documentação:

  • Descriptions em todos os componentes — disponíveis no Dev Mode sem nenhuma ferramenta externa;
  • Descriptions em todas as Variables — incluindo a convenção de uso e o equivalente CSS;
  • Páginas de docs no Figma para os 20 componentes mais usados, com anatomia, variantes e Do's & Don'ts;
  • Zeroheight para a documentação pública — usada onboarding de novos designers e apresentações para stakeholders;
  • Changelog no Figma — uma página "What's New" atualizada a cada release com data, componentes afetados e links para os componentes;
  • Processo: "Docs as DoD" — toda PR de componente inclui atualização de docs como item obrigatório na checklist.

Resultado: o tempo médio de onboarding de novos designers caiu de 3 semanas para 5 dias. Perguntas repetidas sobre uso de componentes caíram 70%.

Resumo

  • Descriptions em components e variables são a forma mais eficiente de documentar — aparecem inline no Dev Mode.
  • Páginas de docs dentro do Figma: anatomia, variantes, Do's & Don'ts, comportamentos, acessibilidade.
  • Annotations documentam comportamentos interativos e regras que o Dev Mode não captura.
  • Ferramentas externas (Zeroheight, Supernova) são ótimas para DS públicos ou com audiência grande, mas têm overhead.
  • Docs atualizada é responsabilidade contínua: "Docs as DoD", revisão periódica, responsável designado.
  • Documentação desatualizada é pior que nenhuma — prefira menos, mas correto.
✍️ Exercício

Documente 3 componentes do seu DS

Escolha 3 componentes do DS que você construiu ao longo deste módulo. Para cada um:

  1. Escreva uma Description no componente com: o que é, quando usar, quando NÃO usar;
  2. Adicione o Documentation Link apontando para qualquer URL relevante (pode ser um artigo, o próprio Figma, ou um link fictício por enquanto);
  3. Crie uma página de docs no arquivo com: nome + status, anatomia com labels, e pelo menos um par de Do's & Don'ts;
  4. Adicione uma Annotation em um frame de exemplo com uma regra de comportamento (ex: "máximo de 50 caracteres neste campo").
Critério de sucesso: ao inspecionar um componente no Dev Mode, a Description aparece completa. A página de docs é clara o suficiente para que alguém que nunca usou o componente saiba exatamente quando e como usá-lo sem fazer perguntas.

QuizTeste seu conhecimento

1. Onde a Description de um componente aparece no Figma sem precisar de ferramentas externas?

  • Somente quando o designer abre o Main Component diretamente
  • No Dev Mode, quando um desenvolvedor inspeciona uma instância do componente
  • No painel de Assets ao passar o mouse sobre o componente
  • Apenas em ferramentas externas como Zeroheight ou Supernova
A Description do componente aparece diretamente no Dev Mode do Figma, tornando-a acessível a desenvolvedores sem precisar de nenhuma outra ferramenta. Esse é um dos argumentos mais fortes para documentar descriptions cuidadosamente.

2. O que são Annotations no Figma e para que servem?

  • Comentários de texto colados como sticky notes no canvas
  • Labels automáticos que o Figma gera com base nos valores das Variables
  • Marcadores estruturados que aparecem no Dev Mode para documentar comportamentos interativos e regras que o inspector não captura automaticamente
  • Notas visíveis somente durante apresentações de Prototype
Annotations são marcadores estruturados criados sobre frames ou componentes. Eles aparecem no Dev Mode e servem para documentar comportamentos que as specs visuais não capturam — como "este header colapsa ao rolar 80 px" ou "validação acontece em blur".

3. Qual é o risco de ter documentação desatualizada em um Design System?

  • O Figma nega a publicação da Library até que a documentação seja atualizada
  • Os componentes ficam bloqueados para edição até que a documentação seja revisada
  • O DS passa a exigir mais espaço de armazenamento
  • Designers seguem regras incorretas, criando inconsistências — documentação errada causa mais dano do que ausência de documentação
Documentação desatualizada induz designers a cometer erros com confiança — eles acreditam estar seguindo as regras, mas estão seguindo regras obsoletas. Isso cria inconsistência sistêmica que é difícil de rastrear e corrigir.
