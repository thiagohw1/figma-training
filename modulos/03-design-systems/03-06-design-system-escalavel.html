Estruturando um Design System escalável

Chegou a hora de juntar tudo: foundations, tokens, Collections, aliases, Modes e convenções de nomenclatura numa arquitetura coerente, construída do zero, passo a passo.

⏱️ Leitura: ~28 min 🎯 Nível: Avançado 🛠️ Pratique no Figma

Ao final desta lição você será capaz de

  • Montar a arquitetura completa de Collections (primitives, semantic, component) para um DS real;
  • Definir as foundations completas: cor, tipografia, espaçamento, radius, sombras e grade;
  • Aplicar naming consistente em todos os níveis de token;
  • Estruturar um arquivo Figma com páginas organizadas seguindo boas práticas de DS;
  • Construir a fundação de tokens do zero num projeto real.

A arquitetura em três camadas

Um Design System escalável no Figma tem três camadas de Collections de Variables, cada uma com uma responsabilidade clara:

A arquitetura em três camadas. Primitives fornecem os valores; Semantic dá contexto; Component tokens específicos permitem overrides sem quebrar a hierarquia.

Foundations completas — o que precisa existir

Antes de criar qualquer componente, você precisa definir todas as foundations. Aqui está o checklist completo:

1. Cor

  • Escala da cor primária: 10 tons (50, 100, 200, 300, 400, 500, 600, 700, 800, 900);
  • Cores semânticas: success (verde), warning (amarelo), danger (vermelho), info (azul);
  • Neutros: 11 tons (0 = branco → 1000 = preto), usados para textos, fundos, bordas;
  • Tokens semânticos: bg/surface, bg/subtle, text/default, text/muted, border/default, border/strong, feedback/success, feedback/warning, feedback/danger, feedback/info.

2. Tipografia

  • Família de fonte: sistema (Inter, -apple-system…) ou fonte da marca;
  • Escala de tamanhos: 12, 14, 16, 18, 20, 24, 28, 32, 40, 48 (tokens Number primitivos);
  • Pesos: 400 (regular), 500 (medium), 600 (semibold), 700 (bold);
  • Line-heights: 1.2 (display), 1.35 (heading), 1.5 (body), 1.7 (relaxed);
  • Text Styles: display-xl, display-lg, heading-xl, heading-lg, heading-md, body-lg, body-md, body-sm, label-lg, label-sm, caption.

3. Espaçamento

Use uma escala de 4 px — todos os valores são múltiplos de 4:

TokenValorUso típico
spacing/14pxMicro gaps, ícones inline
spacing/28pxGaps mínimos entre elementos relacionados
spacing/312pxPadding pequeno de componentes
spacing/416pxPadding padrão de componentes
spacing/624pxPadding generoso, gaps entre seções de card
spacing/832pxPadding de seções, gaps entre cards
spacing/1248pxEspaçamento entre seções de página
spacing/1664pxMargens grandes, seções hero

4. Radius (arredondamento de cantos)

Token semânticoValorUsado em
radius/none0Imagens de borda-a-borda, tabelas
radius/sm4pxTags, badges, tooltips
radius/md8pxInputs, dropdowns, menus
radius/lg12pxCards, modais pequenos
radius/xl16pxModais, sheets, drawers
radius/full9999pxBotões pill, avatares circulares, chips

5. Sombras (Elevation)

  • shadow/sm — sombra muito leve, usada em inputs e elementos de formulário;
  • shadow/md — sombra de cards e surfaces elevadas;
  • shadow/lg — sombra de dropdowns, popovers e tooltips;
  • shadow/xl — sombra de modais e sheets.

Sombras ainda requerem Effect Styles no Figma (não Variables) pois podem ter múltiplas camadas. Mas você pode criar tokens Number para os valores de blur e offset e aplicá-los via Variables às Effect Styles via Code Syntax.

6. Grade e Layout

  • Mobile: 4 colunas, 16 px de margem, 8 px de gutter;
  • Tablet: 8 colunas, 24 px de margem, 16 px de gutter;
  • Desktop: 12 colunas, 32–64 px de margem, 24 px de gutter;
  • Largura máxima de conteúdo: 1200–1440 px dependendo do produto.

Passo a passo: construindo a fundação do zero

Siga esta sequência para montar um DS funcional em um arquivo Figma novo:

  1. Estruture as páginas do arquivo. Crie as páginas: 🏠 Cover, 🎨 Foundations, 📦 Components, 🧩 Patterns, 📄 Templates. A página Foundations concentra todas as samples visuais; as Variables ficam no painel de Variables, não em páginas separadas.
  2. Crie a Collection Primitives/Color. No painel de Variables, crie a Collection. Adicione os tokens primitivos: escala de azul (50–900), escala de verde/vermelho/amarelo para feedback, neutros (0–1000). Sem Modes — primitivos são absolutos.
  3. Crie a Collection Primitives/Number. Adicione a escala de spacing (4, 8, 12, 16, 24, 32, 48, 64), escala de font-size (12, 14, 16, 18, 20, 24, 28, 32), e valores de radius (0, 4, 8, 12, 16, 9999).
  4. Crie a Collection Semantic/Color com Modes Light e Dark. Adicione todos os tokens semânticos como aliases para primitivos. Preencha os dois Modes com os valores corretos. Ative o Scoping correto para cada token.
  5. Crie a Collection Semantic/Spacing. Adicione tokens semânticos de spacing: spacing/component/xs, sm, md, lg; spacing/layout/xs, sm, md, lg; spacing/inset/sm, md, lg. Crie Modes Comfortable e Compact com valores distintos.
  6. Crie a Collection Semantic/Radius. Tokens semânticos: radius/button, radius/input, radius/card, radius/modal, radius/chip, radius/avatar. Cada um aponta para o primitivo correto.
  7. Crie as Text Styles. No painel de Styles, crie os Text Styles usando as fontes e tamanhos definidos. Conecte as cores de texto aos tokens semânticos usando Variables.
  8. Crie as Effect Styles para sombras. Adicione os 4 níveis de sombra como Effect Styles.
  9. Monte as amostras visuais na página Foundations. Na página Foundations, crie um frame por categoria de foundation com amostras — a paleta de cores, a escala de tipos, os ícones, as sombras. Isso serve tanto como documentação visual quanto como teste de que as variables estão corretamente aplicadas.
Commece menor, escale depois

Não precisa criar tudo de uma vez. Comece com as 3 Collections mais importantes: Primitives/Color, Semantic/Color (com Light/Dark) e Primitives/Number. Isso já cobre 80% das necessidades. Adicione Semantic/Spacing, Radius e as demais Collections à medida que os primeiros componentes forem construídos e as necessidades ficarem claras.

Exemplo de uso real

A empresa de software B2B "Ventura" está construindo um DS para seus 3 produtos (CRM, ERP, HCM). A arquitetura escolhida:

  • 4 Collections primitivas (Color, Spacing, Radius, Typography Size) — sem Modes;
  • 3 Collections semânticas (Color com Light/Dark, Spacing com Comfortable/Compact, Radius sem Modes) — usando aliases para primitivos;
  • 1 Collection de Brand com 3 Modes (CRM = azul, ERP = verde, HCM = laranja) — aliases para os primitivos de cor;
  • Text Styles e Effect Styles para tipografia e sombras;
  • Total de 180 tokens. Equipe de 8 designers, todos trabalhando no mesmo arquivo de Library.

Resultado: qualquer um dos 3 produtos pode ser gerado a partir do mesmo arquivo de componentes apenas trocando o Mode de Brand + Light/Dark. 80% de reuso de componentes entre produtos.

Resumo

  • A arquitetura em 3 camadas (Primitives → Semantic → Component) é a base de todo DS escalável.
  • Foundations completas: cor, tipografia, espaçamento, radius, sombras e grade.
  • Use escala de 4 px para spacing e Text Styles para tipografia composta.
  • Sombras ainda precisam de Effect Styles; demais valores numéricos e de cor usam Variables.
  • Naming consistente segue: categoria/grupo/variante/estado em todos os níveis.
  • Comece com 3 Collections, escale conforme a necessidade aparece.
✍️ Exercício

Construa a fundação completa

Crie um arquivo "Meu Design System" e:

  1. Estruture 5 páginas: Cover, Foundations, Components, Patterns, Templates;
  2. Crie as Collections Primitives/Color, Primitives/Number e Semantic/Color (com Modes Light e Dark);
  3. Monte a amostra visual da paleta na página Foundations — grades de cor com os 10 tons de cada família, aplicando as variables de cor;
  4. Crie pelo menos 6 Text Styles cobrindo display, heading, body, label e caption;
  5. Crie 4 Effect Styles para sombras (sm, md, lg, xl).
Critério de sucesso: o arquivo tem todas as foundations definidas, a amostra de paleta muda de aparência ao trocar o Mode do Frame pai para Dark, e todos os elementos usam Variables ou Styles — zero valores hardcoded.
🏆 Desafio

DS para um produto real existente

Escolha um app que você usa frequentemente (pode ser Spotify, iFood, Airbnb, Nubank). Faça um audit visual completo: identifique as cores primárias, secundárias e neutras, a fonte usada, os tamanhos típicos de texto, os padrões de espaçamento e os raios de cantos. A partir desse audit, construa a fundação de tokens do DS desse produto — com Primitives e Semânticos — no Figma. O objetivo não é ser pixel-perfect, mas sim demonstrar que você entende a estrutura do DS subjacente a esse produto.

QuizTeste seu conhecimento

1. Por que sombras ainda requerem Effect Styles em vez de Variables no Figma?

  • Variables não podem armazenar valores relacionados a sombras por limitação técnica
  • Sombras podem ter múltiplas camadas e propriedades compostas (blur, spread, offset, cor), que Variables de tipo único não suportam
  • Effect Styles aparecem no Dev Mode e Variables não
  • Variables de sombra estão disponíveis apenas no plano Enterprise
Effect Styles suportam sombras com múltiplas camadas, combinações de Inner Shadow + Drop Shadow, opacidade e blend modes — uma composição complexa que Variables (que armazenam um único valor primitivo) não conseguem representar.

2. Qual é a escala de espaçamento recomendada na lição para garantir consistência?

  • Escala de 5 px: 5, 10, 15, 20, 25, 30…
  • Escala de 8 px apenas: 8, 16, 24, 32, 64…
  • Escala de 4 px: 4, 8, 12, 16, 24, 32, 48, 64 (múltiplos de 4)
  • Qualquer escala, desde que seja consistente internamente
A escala de 4 px é a mais adotada em Design Systems profissionais. Ela permite granularidade suficiente (4, 8, 12) para componentes densos sem criar valores caóticos, e alinha perfeitamente com grades de 8 px usadas em grids de layout.

3. Por que tokens semânticos de radius (ex: radius/button) são preferíveis a usar tokens primitivos diretamente nos componentes?

  • Tokens semânticos têm nomes mais curtos
  • Tokens primitivos não podem ser vinculados a Corner Radius
  • Tokens semânticos são exportados automaticamente para CSS
  • Permitem mudar o radius de todos os botões alterando um único token semântico, sem tocar em cada instância de componente
Tokens semânticos de radius (radius/button apontando para radius/lg) permitem que uma decisão de design ("botões devem ser mais quadrados") seja implementada mudando um único valor, sem caçar todos os componentes que usam radius.
