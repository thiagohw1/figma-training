Organização e nomenclatura

Um arquivo Figma bem nomeado e organizado é a diferença entre um projeto que escala com o time e um caos digital que ninguém quer abrir. Aprenda as convenções usadas nos melhores times do mundo.

⏱️ Leitura: ~20 min 🎯 Nível: Profissional 🛠️ Pratique junto no Figma

Ao final desta lição você será capaz de

  • Aplicar convenções de nomenclatura consistentes a camadas, frames, componentes, páginas e arquivos;
  • Estruturar as páginas de um arquivo Figma de forma que qualquer pessoa do time entenda ao abrir;
  • Nomear componentes com o padrão Propriedade=Valor que o Figma usa nativamente;
  • Criar um cover de arquivo informativo e cores de seção que organizam visualmente a sidebar;
  • Reconhecer boas práticas de organização que continuam funcionando quando o time cresce.

Por que nomenclatura importa tanto?

Quando você trabalha sozinho, nomes como "Frame 47" ou "Group 3" são inconvenientes mas toleráveis. Num time de 5 ou 15 designers, eles se tornam um problema real: ninguém sabe o que aquele elemento é, qual componente usar, nem onde está o estado que o desenvolvedor precisa inspecionar.

Bons nomes são um investimento de segundos que economiza minutos (ou horas) toda semana. Pense assim: seu colega vai abrir esse arquivo às 22h tentando corrigir algo antes de uma entrega. Nomes claros tornam essa situação suportável.

Nomenclatura como documentação viva

Num arquivo bem nomeado, a sidebar do Figma já é uma documentação: você vê Button/Primary/Hover e entende exatamente o que é. Você não precisa de comentários extras para isso.

Camadas e frames: o básico que o time agradece

A regra de ouro é: qualquer camada que vai para produção precisa de nome descritivo. Camadas de trabalho temporário podem ter nomes genéricos, mas tudo que entra num componente ou numa tela entregável deve ser explícito.

Convenções para camadas

  • Use kebab-case ou Title Case de forma consistente. Escolha uma e não mude. Exemplo: card-header ou Card Header — nunca os dois no mesmo arquivo.
  • Seja específico, não genérico. icon-arrow-right é melhor que Icon. user-avatar é melhor que Oval.
  • Prefixe grupos funcionais. Exemplo: todas as camadas de ícones começam com icon-, todas de ilustração com illo-.
  • Nunca deixe "Frame X" ou "Group X" em entregáveis. Renomeie imediatamente ao criar.

Convenções para frames de tela

Frames de tela (screens) geralmente seguem o padrão: [Plataforma] / [Fluxo] / [Estado]. Por exemplo:

  • Mobile / Checkout / Endereço
  • Web / Dashboard / Vazio
  • Mobile / Onboarding / Passo 3
Use barras para criar hierarquia visual

O Figma trata a barra (/) em nomes de camadas como separador de grupo. Em componentes isso cria submenus no painel de propriedades. Em frames, organiza a sidebar de forma legível quando há dezenas de telas.

Estrutura de páginas: o mapa do arquivo

Um arquivo Figma pode ter dezenas de páginas. Sem uma estrutura definida, você passa tempo procurando coisas em vez de criando. Adote esta estrutura padrão, adaptando conforme a necessidade:

Estrutura padrão de páginas. Adapte conforme o projeto, mas mantenha a consistência dentro do time.

Detalhando cada página

Cover: A primeira página do arquivo serve como capa. Inclua o nome do projeto, a versão atual, quem é o responsável, status (Em andamento, Em revisão, Aprovado) e links úteis (Jira, Notion, repositório). O Figma usa o frame chamado .cover (com ponto) como thumbnail do arquivo no dashboard.

Components: Todos os componentes do projeto ficam aqui, organizados por categoria. Não misture componentes com telas. Essa separação facilita enormemente o handoff.

Designs / Flows: As telas entregáveis. Divida em subpáginas por fluxo se o projeto for grande: Designs — Onboarding, Designs — Home, etc.

WIP (Work in Progress): Aqui ficam os rascunhos, experimentos e variações em teste. É seu playground — pode ser bagunçado, mas isolado do restante.

Archive: Nunca delete telas antigas — mova para Archive. O histórico de versões é valioso para justificar decisões em reuniões futuras.

Nomenclatura de componentes: o sistema Property=Value

O Figma usa a barra (/) para criar hierarquia de componentes e inferir propriedades automaticamente quando você usa Variants. A convenção é:

ComponentName / Propriedade=Valor / Outra=Valor

Exemplos práticos:

Nome do componenteO que o Figma infere
Button / Type=Primary, Size=Large, State=DefaultCria propriedades Type, Size e State no painel de Variants
Input / State=Focus, HasLabel=TrueProperties State e HasLabel com toggle automático
Icon / Name=Arrow, Direction=RightPermite trocar o ícone e a direção pelo painel
Avatar / Size=MD, HasBadge=FalsePropriedade de tamanho e badge boolean
Dica de nomenclatura avançada

Prefixe propriedades booleanas com verbos: HasIcon, ShowLabel, IsDisabled. Assim fica óbvio que são true/false. E evite abreviações obscuras — escreva State=Disabled, não St=Dis.

Organizando componentes com seções no Figma

Use Sections (tecla S) para agrupar componentes por categoria dentro da página Components. Nomeie as seções claramente: Buttons & Links, Form Controls, Navigation, Cards & Lists. Sections aparecem como separadores na busca de componentes.

Cover de arquivo: sua primeira impressão

O cover é o que aparece no dashboard do Figma quando alguém abre o projeto. Um bom cover comunica profissionalismo e organização. Crie um frame de 1600×960 px chamado .cover (com ponto no início — isso instrui o Figma a usá-lo como thumbnail) contendo:

  • Nome do projeto com tipografia clara;
  • Versão atual e data da última atualização;
  • Status visual (badge colorido: Em andamento, Aprovado, Arquivado);
  • Avatar e nome do(s) designer(s) responsável(eis);
  • Links para documentação, Jira ou Notion (como texto ou ícones).

Cores de seção: organização visual na sidebar

O Figma permite colorir frames com cores de marcação (section colors). Clique com o botão direito em um frame na sidebar e escolha Mark as section ou use as cores disponíveis. Um sistema comum:

  • Verde: aprovado / entregue;
  • Amarelo: em revisão / aguardando feedback;
  • Cinza: work in progress;
  • Vermelho: bloqueado / com problema.
Cuidado com convenções pessoais

Cores de seção e sistemas de nomenclatura só funcionam se todo o time seguir as mesmas regras. Documente sua convenção no cover ou num Notion compartilhado. Sem documentação, cada designer vai criar o próprio sistema.

Boas práticas que escalam com o time

  1. Crie um "Guia de nomenclatura" no cover. Inclua um frame na página Cover explicando as convenções adotadas: como nomear camadas, componentes, páginas e frames. Atualize quando o time decidir mudar algo.
  2. Use prefixos de status nos frames de tela. Exemplo: [WIP] Checkout, [REVIEW] Checkout, [DONE] Checkout. Assim você vê o status de cada tela sem abrir o frame.
  3. Organize componentes antes de iniciar o design de telas. Crie os componentes base (botões, inputs, tipografia) na página Components primeiro. Designers que criam componentes e telas ao mesmo tempo acabam com duplicatas e inconsistências.
  4. Revise nomes na retrospectiva do sprint. Reserve 10 minutos ao final de cada sprint para "limpar" o arquivo: renomear frames genéricos, mover WIPs para Archive, atualizar o status no cover.
  5. Ative o plugin "Rename It" para renomeações em lote. Quando você precisa renomear 30 camadas seguindo um padrão, fazer isso uma a uma é inviável. O plugin Rename It (gratuito) suporta variáveis, numeração e expressões regulares.

Exemplo de uso real

O time de design do Airbnb mantém uma convenção chamada Design Language System (DLS) onde cada componente segue rigorosamente o padrão Component/Variant/State. Quando um desenvolvedor inspeciona o arquivo no Dev Mode, o nome do componente no Figma é exatamente o mesmo do componente no código React. Isso elimina uma camada inteira de comunicação.

Em times menores, a mesma lógica se aplica: se o Figma chama o botão de Button/Primary/Default e o CSS chama a classe de .btn-primary, o desenvolvedor precisa mapear manualmente. Se você chamar de Button em ambos, esse mapeamento some.

Exemplo de convenção para um app de finanças

Páginas: Cover · Components · Tokens · Home · Transações · Cartões · Perfil · WIP · Archive
Componentes: Card/Type=Transaction, Status=Pending
Camadas de ícone: icon-arrow-up-green, icon-arrow-down-red
Frames de tela: Mobile / Home / Logged In

Resumo

  • Use kebab-case ou Title Case de forma consistente em todas as camadas e nunca deixe "Frame X" ou "Group X" em entregáveis.
  • Estruture as páginas como: Cover, Components, Designs (por fluxo), WIP e Archive.
  • Nomeie componentes com Propriedade=Valor para que o Figma infira variants automaticamente.
  • Crie um frame .cover de 1600×960 px como thumbnail informativo do arquivo.
  • Use cores de seção para sinalizar status de frames de forma visual.
  • Documente e compartilhe as convenções — elas só funcionam se o time todo seguir.
✍️ Exercício

Organize um arquivo existente

Pegue qualquer arquivo Figma que você tenha e aplique as convenções desta lição:

  1. Crie a estrutura de páginas: Cover, Components, Designs, WIP, Archive.
  2. Renomeie todos os frames genéricos ("Frame 12", etc.) seguindo o padrão Plataforma / Fluxo / Estado.
  3. Crie um frame .cover de 1600×960 px com nome do projeto, versão e status.
  4. Se o arquivo tiver componentes, renomeie-os seguindo o padrão Componente/Propriedade=Valor.
Critério de sucesso: uma pessoa do time que nunca viu o arquivo consegue entender a estrutura em menos de 2 minutos sem precisar perguntar nada.

QuizTeste seu conhecimento

1. Qual é o nome especial que um frame deve ter para aparecer como thumbnail do arquivo no dashboard do Figma?

  • thumbnail
  • cover-image
  • .cover
  • _preview
O frame deve se chamar .cover (com ponto no início). O Figma usa esse nome de forma nativa para identificar o thumbnail do arquivo.

2. Qual convenção de nomenclatura o Figma usa nativamente para inferir propriedades de Variants automaticamente?

  • Propriedade:Valor (com dois-pontos)
  • Propriedade=Valor (com sinal de igual)
  • Propriedade—Valor (com traço longo)
  • Propriedade_Valor (com underline)
O Figma reconhece o padrão Propriedade=Valor (com sinal de igual) para criar automaticamente as propriedades de variantes no painel de design.

3. Qual é a principal função da página "WIP" na estrutura de páginas recomendada?

  • Guardar versões antigas de telas aprovadas
  • Listar todos os componentes do projeto
  • Documentar as decisões de design tomadas
  • Isolar rascunhos e experimentos das telas entregáveis
A página WIP (Work in Progress) serve como playground isolado para rascunhos, experimentos e variações em teste, mantendo as telas entregáveis limpas na página Designs.
