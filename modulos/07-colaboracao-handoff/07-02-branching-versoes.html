Branching e version history

Trabalhar em um design de produto sem controle de versão é como programar sem Git — você não sabe o que mudou, não consegue voltar atrás e cada "tentativa experimental" arriscaa o design principal. Nesta lição você aprende a gerenciar versões e trabalhar de forma isolada com branches.

⏱️ Leitura: ~22 min 🎯 Nível: Profissional 🛠️ Pratique junto no Figma

Ao final desta lição você será capaz de

  • Entender o que é o Version History e como o Figma salva automaticamente;
  • Criar versões nomeadas em marcos importantes do projeto;
  • Restaurar e comparar versões anteriores;
  • Criar e trabalhar em branches para explorar mudanças sem afetar o arquivo principal;
  • Fazer review e merge de uma branch de volta ao arquivo principal.

Version History: o histórico automático do Figma

O Figma salva automaticamente cada mudança que você faz — continuamente, em segundo plano, sem precisar apertar Ctrl + S. Esse histórico de auto-save é o Version History, e ele funciona como uma linha do tempo completa de tudo que aconteceu no arquivo.

Pense nisso como um sistema de commits automático: cada sessão de edição gera um ponto no histórico. Se você quebrar algo, basta voltar a uma versão anterior. Se quiser ver quando uma decisão foi tomada, basta procurar no histórico.

Retenção do histórico por plano

No plano Starter (gratuito), o Figma mantém os últimos 30 dias de histórico automático. Nos planos pagos (Professional, Organization, Enterprise), o histórico é ilimitado — você pode ver literalmente o primeiro traço feito no arquivo desde sua criação.

Passo a passo: acessando o Version History

  1. Abra o menu do arquivo. No modo de edição, clique no nome do arquivo na barra superior para abrir o menu do arquivo (ou use o menu Main Menu → File → Show version history).
  2. Selecione "Show version history". O painel lateral direito se transforma no painel de histórico, mostrando uma lista cronológica de versões com data, hora e nome do editor responsável.
  3. Navegue pelo histórico. Clique em qualquer versão na lista. O canvas se torna somente leitura e mostra o estado do arquivo naquele momento exato. Você pode inspecionar qualquer elemento, zoom, etc.
  4. Compare visualmente. Navegue entre versões para ver o que mudou. O Figma não tem um diff visual automático, mas você pode abrir duas abas do navegador com versões diferentes e comparar lado a lado.
  5. Restaure se necessário. Clique nos três pontos "..." ao lado de uma versão e selecione Restore this version. O arquivo volta àquele estado — e a versão atual automaticamente vira um ponto salvo no histórico antes da restauração, para que você não perca nada.

Criando versões nomeadas

As versões automáticas têm nomes genéricos como "Autosaved". Para criar um marco rastreável — por exemplo, "Aprovado pelo cliente — Sprint 3" — você pode nomear uma versão manualmente:

  1. Acesse o Version History conforme descrito acima.
  2. Clique em "Save current version" no topo do painel, ou use Ctrl + Alt + S (Windows) / ⌘ + ⌥ + S (Mac) diretamente no modo de edição.
  3. Digite um nome descritivo para a versão (ex: "V2 - Aprovada pelo time de produto, 20/01/2026") e clique em Save. Essa versão aparece destacada com um ícone diferente no histórico.
Quando criar versões nomeadas

Crie versões nomeadas em momentos de marco: antes de uma apresentação importante, após aprovação do cliente, ao iniciar uma nova sprint, antes de uma experimentação arriscada, e ao finalizar uma feature. Isso cria uma narrativa do projeto que vale ouro meses depois.

Versões automáticas (pequenos pontos) intercaladas com versões nomeadas (V1, V2, V3) em marcos importantes.

Branching: trabalhando em isolamento

O Branching é um recurso dos planos pagos (Professional e acima) que permite criar uma cópia divergente do arquivo — uma branch — onde você pode fazer mudanças sem afetar o arquivo principal (a "main"). Quando as mudanças estão aprovadas, você faz o merge de volta.

Se você usa Git no desenvolvimento, o conceito é exatamente o mesmo: main é o arquivo estável, branches são experimentos isolados que depois podem ser integrados.

Por que usar branches?

  • Experimentos sem risco: quer testar uma direção visual completamente diferente? Faça numa branch — se não funcionar, descarte sem afetar nada.
  • Trabalho paralelo: dois designers podem trabalhar em features diferentes ao mesmo tempo, cada um na sua branch, sem conflito.
  • Processo de aprovação: branches criam um fluxo formal de review — a mudança não vai para a main até ser revisada e aprovada.
  • Entrega faseada: você pode ter branches para diferentes sprints ou releases em andamento simultaneamente.

Passo a passo: criando e usando uma branch

  1. Abra o menu do arquivo. Clique no nome do arquivo na barra superior para abrir o menu principal do arquivo.
  2. Selecione "Create branch". Na seção de branching, clique em Create branch. O Figma pedirá um nome para a branch — use nomes descritivos como "redesign-header-sprint4" ou "experimento-tipografia-sans".
  3. Trabalhe na branch normalmente. A branch se abre como um arquivo separado. O indicador na barra superior mostra o nome da branch com um ícone de "fork". Faça suas edições aqui sem preocupação com o arquivo principal.
  4. Solicite review (opcional). Quando terminar, compartilhe o link da branch com revisores. Eles podem adicionar comentários diretamente na branch.
  5. Faça o merge para a main. No menu do arquivo da branch, clique em Merge branch. O Figma mostra um preview das mudanças — novos frames, frames modificados e frames deletados — e você confirma o merge. As mudanças aparecem no arquivo principal.
Conflitos de merge

Se alguém modificou os mesmos frames no arquivo principal enquanto você trabalhava na branch, pode haver conflitos. O Figma apresenta um painel de resolução de conflitos onde você escolhe qual versão manter (a da branch ou a da main) para cada frame em conflito. Revise com cuidado antes de confirmar.

Visualizando diferenças antes do merge

Antes de confirmar o merge, o Figma exibe um painel de diferenças (diff view) que mostra lado a lado:

  • Frames novos (existem na branch mas não na main);
  • Frames modificados (existem em ambas, mas com diferenças);
  • Frames deletados (existem na main mas foram removidos na branch).

Você pode navegar por cada diff, inspecionar as mudanças e optar por incluir ou excluir frames específicos do merge.

Branching é exclusivo de planos pagos

O recurso de branching está disponível apenas nos planos Professional, Organization e Enterprise. No plano Starter (gratuito), você pode simular o conceito duplicando o arquivo manualmente — mas sem o merge integrado.

Exemplo de uso real

Uma startup de fintech está redesenhando o fluxo de onboarding. O time tem dois designers:

  • Designer A cria uma branch "onboarding-v2-stepbystep" para redesenhar o fluxo com etapas progressivas;
  • Designer B cria "onboarding-v2-singlepage" para uma abordagem em página única com scroll;
  • Ambos trabalham por uma semana sem interferência. O arquivo principal continua estável para o time de dev que está implementando a v1;
  • Na sprint review, o time vota: a abordagem step-by-step vence;
  • Designer A faz o merge da sua branch para a main, e a branch de B é descartada sem deixar rastro;
  • Uma versão nomeada "Onboarding V2 aprovado — 28/01/2026" é criada na main como marco.
Branches como processo de aprovação

Em times maiores, é comum ter uma regra: "nenhuma mudança vai para a main sem passar por uma branch com aprovação de pelo menos um outro designer". Isso cria um processo de code review para design — aumenta a qualidade e distribui o conhecimento do sistema.

✍️ Exercício

Histórico e versões nomeadas

Pratique o Version History em um arquivo seu:

  1. Abra um arquivo existente e faça 3 ou 4 mudanças sequenciais (mova elementos, mude cores, altere textos).
  2. Acesse o Version History (menu do arquivo → Show version history).
  3. Navegue pelas versões automáticas e confirme que consegue ver cada estado do design.
  4. Salve uma versão nomeada: Ctrl/⌘ + Alt/⌥ + S com o nome "Exercício módulo 7 — versão inicial".
  5. Faça mais uma mudança drástica (delete algo importante), depois restaure a versão nomeada.
Critério de sucesso: a versão nomeada aparece destacada no painel de histórico, e após a restauração o arquivo volta exatamente ao estado em que foi salvo — o elemento deletado reaparece.
🏆 Desafio

Fluxo completo de branch e merge

Se você tem acesso a um plano pago: crie uma branch a partir de um arquivo de design, redesenhe de forma significativa pelo menos 3 telas na branch (mudança de layout, não apenas cores), depois faça o merge de volta à main usando o diff view para revisar cada mudança antes de confirmar. Documente o processo com uma versão nomeada "Pós-merge sprint X" após o merge. Se estiver no plano gratuito: simule duplicando o arquivo, faça as mudanças na cópia e documente quais frames seriam "mergeados" usando comentários.

QuizTeste seu conhecimento

1. O que acontece com o arquivo quando você restaura uma versão anterior no Figma?

  • O histórico é deletado permanentemente
  • Apenas os frames selecionados voltam ao estado anterior
  • O arquivo volta ao estado daquela versão, e o estado atual é salvo automaticamente como um ponto no histórico antes da restauração
  • Uma cópia do arquivo atual é criada antes da restauração, separada do arquivo principal
O Figma é seguro: ao restaurar, ele salva automaticamente o estado atual como um ponto no histórico antes de restaurar a versão escolhida — você nunca perde trabalho feito.

2. Em quais planos do Figma o recurso de Branching está disponível?

  • Professional, Organization e Enterprise (planos pagos)
  • Todos os planos, incluindo o Starter gratuito
  • Apenas no plano Enterprise
  • Starter e Professional
O Branching é um recurso exclusivo dos planos pagos: Professional, Organization e Enterprise. O plano Starter gratuito não tem acesso a branches.

3. Qual é o principal benefício de criar versões nomeadas no Version History?

  • Aumentar o limite de retenção do histórico no plano gratuito
  • Criar marcos rastreáveis com contexto — como "Aprovado pelo cliente sprint 3" — facilitando encontrar e restaurar estados importantes no futuro
  • Bloquear o arquivo para edições até que a versão seja aprovada
  • Sincronizar o arquivo com um repositório Git externo
Versões nomeadas criam marcos rastreáveis com contexto humano — muito mais útil que "Autosaved 14:32:07". Elas ficam destacadas no histórico e são fáceis de encontrar quando você precisar voltar meses depois.
