Handoff profissional

Um handoff ruim transforma um design perfeito em implementação medíocre — e culpar o desenvolvedor não adianta nada. A responsabilidade pelo handoff é do designer. Nesta lição você aprende a preparar e entregar designs com clareza absoluta, usando todas as ferramentas que o Figma oferece para isso.

⏱️ Leitura: ~25 min 🎯 Nível: Profissional 🛠️ Pratique junto no Figma

Ao final desta lição você será capaz de

  • Usar Annotations para documentar specs e intenções diretamente no canvas;
  • Organizar o arquivo Figma para máxima clareza na entrega;
  • Comunicar estados, comportamentos e edge cases com precisão;
  • Executar uma checklist completa de handoff antes de passar para o time de dev;
  • Manter uma comunicação eficiente com desenvolvedores durante a implementação.

Por que o handoff é responsabilidade do designer

Existe um mito no mundo do design de produto: "o design é meu trabalho, a implementação é trabalho deles". Na realidade, a qualidade da implementação depende diretamente da qualidade da entrega do designer. Um design ambíguo — sem estados, sem medidas explícitas, sem documentação de comportamentos — garante uma implementação problemática, independente da competência do desenvolvedor.

O handoff profissional não é sobre criar "mais documentação" — é sobre antecipar perguntas. Cada pergunta que o dev não precisar fazer durante a implementação é tempo economizado para o projeto inteiro.

O custo de um handoff ruim

Estudos de processos ágeis mostram que uma pergunta não respondida no design gera em média 3 idas e vindas entre dev e designer, custando entre 2–4 horas de trabalho combinado. Um arquivo com 20 ambiguidades = 40–80 horas de retrabalho. Um handoff bem feito que leva 2h extras no design economiza dias no desenvolvimento.

Annotations: documentando no canvas

As Annotations são notas de design que ficam visíveis no Dev Mode mas são ocultas no modo de edição normal — perfeitas para comunicar intenções técnicas sem poluir o canvas de design.

Como adicionar annotations

  1. No Dev Mode, ative o painel de Annotations. No modo de edição, vá em Main Menu → Plugins → Annotations ou use o painel de anotações no Dev Mode (ícone de nota no painel esquerdo).
  2. Selecione um elemento e adicione uma nota. Com o elemento selecionado, clique em "Add annotation". Uma caixa de texto vinculada ao elemento aparece no canvas. As annotations ficam ancoradas ao elemento — se ele se mover, a nota o acompanha.
  3. Escreva a spec técnica ou a intenção de comportamento. Exemplos: "Animação de entrada: fade-in 200ms ease-out", "Truncar com reticências após 2 linhas", "Placeholder desaparece ao focar — não usar float label aqui".
  4. As annotations ficam visíveis no Dev Mode. Quando o dev acessa o Dev Mode, vê todas as annotations ancoradas aos elementos correspondentes — exatamente onde ele precisa da informação.

O que documentar com annotations

  • Comportamentos de interação: "ao clicar, exibir dropdown com 4px de deslocamento para baixo";
  • Animações e transições: "expand/collapse: height auto, 250ms, ease-in-out";
  • Edge cases de texto: "máximo 3 linhas antes de truncar com '...'";
  • Acessibilidade: "alt text: 'Foto de perfil de [nome do usuário]'";
  • Responsividade: "em mobile, empilhar verticalmente; em desktop, lado a lado";
  • Lógica condicional: "este badge só aparece quando unread_count > 0".
Annotations vs. comentários: qual usar?

Use annotations para specs técnicas permanentes que o dev precisa consultar durante toda a implementação. Use comentários para discussões, perguntas e feedbacks que precisam de resposta e serão resolvidos. Annotations são documentação; comentários são conversa.

Organizando o arquivo para entrega

Um arquivo bem organizado reduz drasticamente a confusão no handoff. Existem convenções que o time inteiro deve conhecer:

Estrutura de páginas

Organize o arquivo em páginas com papéis claros:

Nomeando frames e layers

Nomes descritivos são fundamentais. Compare:

  • Ruim: "Frame 47", "Rectangle 3", "Group 12"
  • Bom: "Home/Mobile/Feed", "Button/Primary/Default", "Card/Product/Compact"

Use barras (/) para criar hierarquia semântica — o Figma respeita essa convenção em vários lugares (painel de componentes, Dev Mode, plugins).

Usando o status "Ready for dev"

Marque frames como Ready for dev apenas quando:

  • O design foi revisado por pelo menos outro designer;
  • O PM/stakeholder aprovou o fluxo;
  • Todos os estados do componente estão documentados;
  • As annotations de comportamento estão preenchidas;
  • Os assets exportáveis estão configurados.

Documentando estados e comportamentos

Um dos maiores erros de handoff é entregar apenas o estado padrão (default) de uma interface, esquecendo todos os outros. Para cada componente interativo, documente:

EstadoQuando ocorreO que muda visualmente
DefaultEstado inicial, sem interação—
HoverMouse sobre o elementoCor de fundo, cursor, sombra
FocusFoco via teclado ou tabOutline de foco (crítico para acessibilidade)
Active/PressedDurante o cliqueEstado pressionado (scale, sombra, cor)
DisabledAção indisponívelOpacidade reduzida, cursor not-allowed
LoadingAguardando resposta assíncronaSpinner, skeleton, texto alternativo
ErrorValidação falhou ou erro de sistemaCor vermelha, mensagem de erro, ícone
SuccessAção concluída com sucessoCor verde, checkmark, mensagem
EmptySem dados para exibirEmpty state ilustrado ou mensagem
O estado que todos esquecem: focus

O estado de focus (visível quando o usuário navega com o teclado) é frequentemente ausente dos designs. Isso é um problema crítico de acessibilidade — a WCAG 2.1 exige que todos os elementos interativos tenham um indicador de foco visível (critério 2.4.7). Inclua sempre o estado de focus no seu handoff.

Comunicando espaçamento e grid

Além das medidas individuais dos componentes, documente o sistema de espaçamento global:

  • Base unit: qual o menor incremento de espaço (geralmente 4px ou 8px);
  • Escala de espaçamento: os valores da escala (4, 8, 12, 16, 24, 32, 48...);
  • Grid de colunas: quantas colunas, largura das colunas, gutters, margens externas;
  • Breakpoints: mobile, tablet, desktop, wide — e como o layout muda em cada.

O ideal é ter uma página "Specs" dedicada com exemplos visuais de cada valor da escala de espaçamento e a grade de layout.

A checklist de handoff

Antes de marcar qualquer tela como "Ready for dev", passe por esta checklist:

📋 Checklist de handoff

Verificação completa antes da entrega

  • Organização
    • Todos os frames têm nomes descritivos (sem "Frame 47" ou "Group 3")
    • Layers e grupos internos estão nomeados e organizados
    • Telas prontas estão na página "Ready for Dev"
    • Rascunhos e WIP estão em páginas separadas e claramente marcados
  • Completude dos estados
    • Default, hover, focus, active, disabled, loading, error, success, empty
    • Estados de validação de formulários (erros, sucesso, em progresso)
    • Empty states para listas e feeds
    • Responsividade (mobile, tablet, desktop) onde aplicável
  • Specs e documentação
    • Annotations de comportamento preenchidas para interações não óbvias
    • Animações e transições documentadas (duração, easing, trigger)
    • Edge cases de texto documentados (textos longos, truncamento, zero resultados)
    • Regras de acessibilidade anotadas (alt texts, ARIA labels, order de foco)
  • Assets e exportação
    • Ícones configurados para export como SVG
    • Imagens configuradas para export em 1x, 2x, 3x
    • Ilustrações e assets especiais com export configurado
  • Design system
    • Componentes usando instâncias da biblioteca (não cópias manuais)
    • Cores usando styles ou variables (não valores literais soltos)
    • Tipografia usando text styles
    • Espaçamentos usando a escala definida (não valores arbitrários)
Padrão de qualidade: um desenvolvedor deve conseguir implementar qualquer tela sem precisar perguntar ao designer — todas as informações necessárias devem estar no arquivo.

Comunicação com devs durante a implementação

O handoff não termina quando você entrega o arquivo — ele termina quando o feature está em produção. Durante a implementação, mantenha:

  • Disponibilidade para perguntas: responda rápido; cada pergunta não respondida é um bloqueio para o dev;
  • Canal definido: combine onde as perguntas devem ser feitas (comentários no Figma, Slack, Jira) — não misture canais;
  • Revisão de implementação: agende uma sessão para revisar o componente implementado antes de ir para produção — "design QA";
  • Documentação de decisões: quando uma pergunta revelar uma ambiguidade no design, resolva-a E documente a resposta como annotation para que outros também vejam;
  • Flexibilidade inteligente: algumas specs podem ser difíceis de implementar por limitações técnicas. Esteja aberto a negociar, mas entenda o impacto visual antes de aceitar.
Design QA: a última milha do handoff

Reserve tempo na sprint para revisar a implementação antes do merge para main. Crie uma lista de itens que não batem com o design e priorize por impacto visual. Itens de 1px a mais num padding raramente valem o custo de reabrir um PR — saiba escolher suas batalhas. Itens de acessibilidade, contraste e comportamento de erro sempre valem.

Exemplo de uso real

Um designer está entregando o redesign da tela de cadastro de um app de saúde. O processo de handoff profissional:

  1. Cria a página "Cadastro V2 - Ready for Dev" com apenas os 7 frames aprovados;
  2. Marca todos os 7 frames como "Ready for dev" no Dev Mode;
  3. Adiciona annotations: "campo CPF aceita formato com ou sem pontuação" e "mostrar/ocultar senha: ícone toggled, não dois campos separados";
  4. Documenta todos os estados dos campos de input: default, focus, filled, error, disabled;
  5. Configura exports para os 3 ícones usados na tela (SVG);
  6. Verifica que todos os componentes são instâncias da biblioteca, não cópias;
  7. Faz uma walkthrough de 15 min ao vivo com o dev para alinhar os comportamentos mais complexos;
  8. 3 dias depois, revisa a implementação no staging e deixa 2 comentários de ajuste — nada crítico, apenas polish.

Resumo

  • O handoff é responsabilidade do designer — ambiguidades no design viram bugs na implementação.
  • Annotations documentam specs técnicas e comportamentos diretamente no canvas, visíveis no Dev Mode.
  • Organize o arquivo com páginas específicas: Ready for Dev, Design (WIP), Components, Specs, Archive.
  • Documente todos os estados: default, hover, focus, active, disabled, loading, error, success, empty.
  • Use a checklist de handoff antes de marcar qualquer tela como pronta — um dev deve conseguir implementar sem perguntas.
  • Mantenha disponibilidade durante a implementação e reserve tempo para Design QA.
✍️ Exercício

Handoff completo de um formulário

Escolha um formulário simples de 2–3 campos (login, contato ou cadastro) e prepare um handoff completo:

  1. Crie uma página "Formulário - Ready for Dev" e mova os frames finalizados para lá.
  2. Documente todos os estados de pelo menos um campo de input (default, focus, filled, error, disabled).
  3. Adicione annotations para pelo menos 3 comportamentos não óbvios (ex: validação, mensagem de erro, comportamento do botão de submit).
  4. Configure o export do ícone de alerta/erro como SVG.
  5. Marque todos os frames como "Ready for dev".
  6. Passe pela checklist de handoff e corrija os itens pendentes.
Critério de sucesso: um desenvolvedor que nunca viu o design deve conseguir implementar o formulário completo (incluindo todos os estados e comportamentos) apenas com o que está no arquivo Figma — sem precisar perguntar nada.
🏆 Desafio

Revisão cruzada de handoff

Troque um arquivo de design com um colega designer. Tente "implementar" o design dele apenas com as informações disponíveis no Figma — sem fazer perguntas verbalmente. Anote cada vez que você ficou em dúvida sobre algo. Depois, compile a lista de dúvidas e compartilhe com o colega como feedback sobre o handoff. Faça o mesmo processo invertido: receba o feedback sobre o seu arquivo. Use o feedback para preencher as lacunas identificadas com annotations e estados faltantes.

QuizTeste seu conhecimento

1. Qual a diferença principal entre Annotations e Comentários no Figma?

  • Annotations são visíveis apenas para o designer; comentários são visíveis para todos
  • Annotations são documentação técnica permanente visível no Dev Mode; comentários são para discussões e feedbacks que serão resolvidos
  • Annotations precisam de um plugin pago; comentários são gratuitos
  • Comentários ficam vinculados a elementos; annotations ficam no canvas livre
Annotations são documentação permanente de specs técnicas — "animação de 200ms fade-in", "truncar após 2 linhas" — visíveis no Dev Mode para consulta durante toda a implementação. Comentários são conversas que têm início, meio e fim (são resolvidos).

2. Qual estado de interface é crítico para acessibilidade e frequentemente esquecido nos handoffs?

  • Estado hover
  • Estado loading
  • Estado disabled
  • Estado focus (indicador de foco via teclado)
O estado de focus é exigido pela WCAG 2.1 (critério 2.4.7) e frequentemente ausente nos designs. Ele deve ser visível quando o usuário navega com teclado — essencial para acessibilidade de pessoas com deficiência motora ou que não usam mouse.

3. Quando um designer deve marcar um frame como "Ready for dev" no Dev Mode?

  • Apenas após aprovação do design, documentação de todos os estados, annotations preenchidas e assets configurados para export
  • Assim que terminar de criar o frame, para o dev poder acompanhar o progresso
  • Quando o cliente aprovar verbalmente em reunião, mesmo sem documentação formal
  • Apenas na última sprint, nunca durante o desenvolvimento iterativo
"Ready for dev" é um contrato: significa que o frame está completo e aprovado. Marcar prematuramente gera retrabalho quando o dev implementa algo que ainda vai mudar. A boa prática é marcar apenas após aprovação, com todos os estados e annotations documentados.
